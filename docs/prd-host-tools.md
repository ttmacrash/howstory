# 하우-스토리 (How-Story) 1단계 PRD: 호스트 운영 도구 (v0.2)

작성: 2026-09-30 · 상태: 초안 · 상위 문서: `docs/platform-architecture.md` (도메인 D1·D2·D4·D7·D8)

## 1. 한 줄 정의

숙소 호스트가 OTA(에어비앤비·야놀자·여기어때 등)에 올린 숙소의 **운영 업무**를 한 곳에서 처리하게 해주는 도구.
안내서 제작, 예약 통합 캘린더, 게스트 안내 메시지, 청소·정비 관리를 다룬다. 예약·결제는 2단계에서 다룬다.

## 2. 배경과 문제

지금 하우-스토리 repo에는 호스트인 JJ가 직접 겪은 불편을 해결한 것들이 이미 있다.

| 이미 만든 것 | 해결한 불편 |
|---|---|
| 스테이 숙소 페이지(`stay/`) | OTA 밖에서 숙소를 보여줄 곳이 없다 |
| 에어비앤비 iCal 예약 감시 + 카카오톡 알림(`scripts/`, `.github/workflows/`) | 새 예약·취소를 앱 열어보기 전에는 모른다 |
| 다국어 안내서 샘플(영·중·일) | 같은 질문을 게스트마다 반복해서 받는다 |

이 셋은 모두 "호스트 운영"이라는 한 문제의 조각이다. 다른 호스트도 같은 조각을 각자 손으로 만들고 있다. 1단계는 이 조각들을 **누구나 쓰는 도구**로 일반화하는 것이다.

## 3. 목표와 비목표

**목표**
- 여러 OTA 예약을 한 캘린더에서 보고, 새 예약·취소를 카카오톡으로 받는다. 이중 예약이 생기지 않는다.
- 호스트가 숙소를 등록하면 그 데이터가 2단계 예약 플랫폼의 숙소 정보로 그대로 이어진다.
- 게스트에게 보내는 안내(체크인, 와이파이, 룰)를 4개 언어로 한 번만 만들어 반복해 쓴다.
- 체크인 안내 같은 반복 메시지를 템플릿으로 보내거나 복사해 쓸 수 있다.
- 호스트가 자기 운영 자산(안내서, 게스트 기록, 리뷰)을 OTA 밖에 소유한다.

**비목표(2단계 이후)**
- 게스트가 숙소를 검색·예약·결제하는 기능
- 호스트 간 순위, 노출, 광고
- 다이내믹 프라이싱

## 4. 사용자

**1차 사용자: 호스트.** 숙소 1~3개를 OTA에 올려 운영하는 개인·소규모 호스트. 본인이 청소하거나 청소 담당자 한두 명을 둔다. 내국인·외국인 게스트를 모두 받는다.

**간접 사용자: 게스트.** 안내서와 안내 메시지를 받는 사람. 내국인과 외국인을 **모두** 대상으로 한다. 따라서 게스트가 보는 모든 화면과 문구는 한국어·영어·중국어·일본어 4개 언어를 기본으로 한다.

**보조 사용자: 청소·정비 담당자.** 체크아웃 후 할 일 목록과 알림만 받는다. 로그인 없이 링크로 접근한다.

## 5. 핵심 원칙

1. **호스트가 직접 사용자다.** JJ 본인 숙소로 먼저 쓰고(도그푸딩), 불편한 것부터 고친다.
2. **OTA를 대체하지 않고 얹는다.** 1단계에서 예약은 여전히 OTA에서 일어난다. 우리는 그 예약을 읽어와 운영을 돕는다.
3. **게스트 국적을 가리지 않는다.** 언어 전환은 게스트 화면의 기본 기능이지 부가 기능이 아니다.
4. **안내서는 데이터다.** 이미지 위에 글자를 박는 것이 아니라, 항목·문구·이미지를 구조화해 저장하고 언어별로 렌더링한다. 그래야 한 번 고치면 4개 언어에 반영된다.

## 6. 기능 요구사항

우선순위: P0 = 1단계 출시 필수, P1 = 출시 직후, P2 = 이후. 도메인 번호는 플랫폼 구조 문서를 따른다.

### F1. 숙소 등록 (P0 · D2)
- 호스트 계정 생성(이메일 또는 카카오 로그인).
- 숙소 기본 정보: 이름, 주소, 유형, 최대 인원, 체크인·체크아웃 시간, 사진, 편의시설, 하우스 룰, 비상 연락처.
- 지금 `config.js`의 `HOWSTORY_STAY`에 하드코딩된 값을 이 데이터로 옮긴다.
- 한 호스트가 숙소를 여러 개 가질 수 있다.
- 여기서 입력한 데이터는 2단계 숙소 상세 페이지의 원본이 된다. 처음부터 언어별 콘텐츠(ListingContent) 구조로 저장한다.

### F3. 예약 통합 캘린더 (P0 · D4)
- OTA별 iCal 주소를 등록하면 주기적으로 읽어 한 캘린더에 합친다. 에어비앤비는 지금 `scripts/airbnb-watch.mjs`가 하는 일을 그대로 가져온다.
- OTA 밖 예약(지인, 전화)은 수동 입력.
- 같은 날짜에 두 예약이 겹치면 경고.
- 새 예약·변경·취소를 감지하면 호스트에게 카카오톡으로 알린다(현재 기능 유지).
- 확인 필요: 야놀자·여기어때의 iCal 제공 여부. 제공하지 않으면 해당 채널은 수동 입력으로 시작한다.

### F2. 게스트 안내서 (P1 · D8)
- 안내서는 **섹션**의 목록이고, 섹션은 **블록**(제목, 본문, 이미지, 이미지+콜아웃, 주의 문구)의 목록이다.
- 기본 템플릿 제공: 체크인 방법, 와이파이, 가전 사용법(세탁기·에어컨·인덕션·TV), 쓰레기 배출, 하우스 룰, 주변 정보, 비상 연락처.
- 문구는 한국어로 쓰면 영·중·일 초안을 자동 번역으로 채우고, 호스트가 언어별로 고칠 수 있다. 번역본이 원문보다 오래되면 "번역 확인 필요" 표시.
- 이미지+콜아웃 블록: 사진 위에 번호 핀을 찍고, 핀마다 4개 언어 설명을 단다.
- 출력: 게스트용 웹 링크(언어 자동 감지 + 수동 전환), QR 코드, 인쇄용 PDF(숙소에 비치).
- 게스트 링크는 로그인 없이 열리고, 숙소별로 켜고 끌 수 있다.

### F4. 게스트 안내 메시지 (P1 · D7)
- 시점별 템플릿: 예약 확정 직후, 체크인 하루 전, 체크인 당일, 체크아웃 당일.
- 템플릿에는 안내서 링크, 도어록 비밀번호, 체크인 시간 같은 변수가 들어간다.
- 게스트 언어에 맞춰 4개 언어 중 하나로 만들어진다.
- 발송 방식은 두 단계로 나눈다.
  - 1단계: **복사해서 OTA 메시지창에 붙여넣기.** OTA는 게스트 전화번호를 가리므로 직접 발송이 불가능한 경우가 많다.
  - 2단계: 게스트가 안내서 링크에서 연락처를 남기면 카카오 알림톡(내국인)·이메일(외국인)로 직접 발송.

### F5. 청소·정비 관리 (P1 · D8)
- 체크아웃이 잡히면 청소 할 일이 자동 생성된다.
- 숙소별 체크리스트(침구 교체, 세제 보충, 소모품 확인)와 완료 사진.
- 담당자는 로그인 없이 카카오톡으로 받은 링크에서 체크한다.
- 고장·파손은 사진과 함께 기록해 정비 목록에 남긴다.

### F6. 게스트 기록과 리뷰 (P2 · D9)
- 예약 단위로 게스트 메모(요청 사항, 특이사항)를 남긴다.
- 안내서 링크에서 게스트가 남긴 후기를 모아 `review/` 페이지처럼 노출할 수 있다.

## 7. 게스트 화면 요구사항 (안내서 뷰어)

- 첫 진입 시 브라우저 언어로 자동 선택, 상단에서 한·영·중·일 전환.
- 모바일 우선. 숙소 와이파이가 안 잡힌 상태에서도 볼 수 있게 핵심 섹션(와이파이 비밀번호, 체크인 방법)은 가볍게.
- 이미지+콜아웃 블록은 사진과 핀 설명을 나란히 보여준다. 확대 가능.
- 호스트 연락 버튼: 카카오톡 채널 링크(내국인), 이메일 또는 WhatsApp 링크(외국인). 호스트가 채널을 고른다.

## 8. 비기능 요구사항

- **다국어**: 게스트 화면의 모든 고정 문구도 4개 언어 리소스로 관리한다.
- **개인정보**: 게스트 정보는 이름·언어·체크인 날짜 정도만 저장한다. 연락처는 게스트가 직접 남길 때만 받고 체크아웃 후 30일 뒤 삭제한다.
- **데이터 소유**: 호스트는 안내서와 예약 기록을 언제든 내보낼 수 있다(JSON, PDF).
- **가용성**: 안내서 뷰어는 정적으로 배포해 백엔드가 죽어도 열린다.

## 9. 시스템 구조

현재 구조는 GitHub Pages 정적 사이트 + GitHub Actions 크론 + Supabase(신청 저장)다. 호스트 도구는 로그인과 데이터 저장이 필요하므로 다음처럼 확장한다.

```
[호스트 웹앱]  ──▶  [Supabase: Auth · Postgres · Storage]
      │                       ▲
      │                       │ iCal 수집 (Edge Function 또는 GitHub Actions 크론)
      ▼                       │
[게스트 안내서 뷰어]  ◀── 안내서 데이터 → 정적 렌더링(언어별)
      │
[카카오톡 알림 · 알림톡]
```

- Supabase는 이미 `config.js`에 연결돼 있어 그대로 확장한다.
- 안내서 뷰어는 저장 시점에 언어별 정적 페이지로 만들어 두고 CDN에서 서빙한다.

**도메인 모델**

| 엔티티 | 주요 속성 |
|---|---|
| Host | id, 이름, 로그인 수단, 알림 채널(카카오) |
| Property | host_id, 이름, 주소, 인원, 체크인·아웃 시간, 사진, 편의시설, 룰 |
| Guide | property_id, 상태(공개/비공개), 기본 언어 |
| GuideSection | guide_id, 순서, 템플릿 종류, 제목(언어별) |
| GuideBlock | section_id, 순서, 유형(text/image/callout/notice), 내용(언어별), 이미지, 핀 좌표 |
| CalendarSource | property_id, 채널(airbnb/yanolja/manual), iCal URL, 마지막 동기화 |
| Booking | property_id, source_id, 체크인, 체크아웃, 게스트명, 언어, 상태 |
| MessageTemplate | property_id, 시점, 본문(언어별), 변수 |
| Task | booking_id, 유형(청소/정비), 담당자, 체크리스트, 상태, 사진 |

## 10. 단계별 계획

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0. 도그푸딩 | JJ 숙소 하나로 F1·F3을 쓴다. 기존 iCal 감시와 카카오 알림을 새 구조로 옮긴다. | 통합 캘린더에서 에어비앤비 예약이 보이고 알림이 온다 |

| 2. 예약 플랫폼 | 플랫폼 구조 문서 8장의 2단계. 별도 PRD. | 첫 결제 예약 완료 |

## 11. 성공 지표 (1단계)

- 숙소당 안내서 생성 완료율(등록 후 7일 안에 공개한 비율)
- 게스트 안내서 열람률(예약 수 대비 링크 열람 수)
- 호스트가 게스트에게 받는 반복 질문 수 감소(호스트 설문)
- 주간 활성 호스트 수

## 12. 리스크와 확인할 것

| 항목 | 내용 | 확인 방법 |
|---|---|---|
| OTA iCal 지원 | 야놀자·여기어때가 iCal을 주는지 불확실 | 호스트 센터 확인, 없으면 수동 입력으로 시작 |
| OTA 약관 | 게스트를 외부 채널로 유도하는 것을 제한할 수 있음 | 에어비앤비 호스트 약관 확인. 안내서 링크는 "숙소 이용 안내"라 허용 범위로 판단되나 확인 필요 |
| 알림톡 발송 요건 | 카카오 알림톡은 비즈니스 채널과 발송 대행사 계약 필요 | 1단계는 호스트 개인 카카오톡 알림(현재 방식)으로 충분 |
| 자동 번역 품질 | 안내 문구 오역은 게스트 불만으로 직결 | 호스트 검수 단계를 필수로 두고, 검수 전 번역은 "초안" 표시 |
| 숙박업 규제 | 도구 단계에서는 우리가 예약을 중개하지 않으므로 직접 적용되지 않음. 2단계 진입 전 재검토 | 2단계 PRD에서 다룸 |

## 13. 열린 질문

1. 호스트 로그인은 카카오만으로 충분한가, 이메일도 둘 것인가.
2. 안내서 자동 번역에 어떤 번역 API를 쓸 것인가(비용·품질).
3. 청소 담당자에게 카카오톡 링크를 보낼 때 호스트 개인 카카오 계정을 쓸 것인가.
4. 1단계에서 유료화를 시도할 것인가, 베타는 무료로 갈 것인가.
